1. What GrabLab CMS v1.0.0 Means for You

Version 1.0.0 marks GrabLab CMS as production-ready. With the core features from v0.1.0 through v0.4.0 complete, this release freezes the public data structures, theme format, APIs, AI authoring guardrails, and server deployment setup so your website and themes can grow without breaking changes across all v1.x releases.

For Site Owners & Editors

  • Safe by Design: No third-party plugin ecosystem to break updates or open backdoors.
  • Smart Redirect Memory: Rename a post or product web address anytime — GrabLab automatically creates a permanent 301 redirect from the old link and updates navigation menus cleanly.
  • Exact Numbers & Prices: Custom currency or decimal fields preserve exact trailing digits (such as 149.9500) via GrabDecimal.
  • One-Time Setup Lock: Once your first administrator creates an account at /setup, public signup closes automatically.

For Designers & Theme Builders

  • One Active Theme Rule: Only one theme renders the site at a time, eliminating conflicting stylesheets and template overrides.
  • Coded or Visual Themes: Build traditional .grab.html templates (like default-starter) or design visually via Grex Theme Builder (mode: "visual" + grex.elements.json).
  • Zero Bloat HTML: Starter templates, visual renders, and Admin screens contain zero wrapper <div> tags — using native semantic elements throughout.

For AI-Assisted Publishing (grab mcp)

  • Scoped Access Tokens: Generate role-based MCP tokens inside the dashboard.
  • Draft-Only Safety: AI tools can prepare new posts (create_entry_draft), but GrabLab strictly forces every AI-created entry into draft status for human review.
  • Accessibility Gate: Layout updates via update_entry_layout automatically block unsafe HTML, missing image descriptions, or skipped heading levels with a clear 422 error.

For Operators & Hosting

  • Immutable Container Profile: Ready-to-run deploy/docker-compose.yml executes with a --read-only root filesystem.
  • Isolated Writable Storage: Only storage/, uploads/, and /static/grex/ are writable.
  • Multi-Database Parity: Cumulative migrations (001–003) work consistently across SQLite, PostgreSQL, and MariaDB.
  • Built-In Health Probes: Ready for load balancers and containers via /_health and /_ready.

4. Quickstart & Production Deployment Guide

A. Local Quickstart (Windows / Development)

grab migrate --db-config grab.data.json --allow-db main:migrate migrations/003_v04_schema.grab
grab run --db-config grab.data.json --allow-db main:read-write --allow-read . migrations/seed.grab
grab serve --addr 127.0.0.1:8080 --allow-scripts --db-config grab.data.json --allow-db main:read-write --platform-config grab.platform.json --allow-cache cms:read-write --allow-cache cms:limit --allow-env GRABLAB_MASTER_KEY,GRABLAB_UPLOAD_DIR,GRABLAB_MAX_UPLOAD_BYTES --allow-read . --allow-write uploads --static public src/app.grab

Then open http://127.0.0.1:8080/setup in your browser to create your primary administrator account.

B. Production Hardened Docker Deployment (--read-only)

Use the bundled template in deploy/docker-compose.yml. Keep all secrets (like GRABLAB_MASTER_KEY) and real server IP addresses in an untracked .env file outside Git:

# Inside deploy/ (after placing secrets in .env)
docker compose up -d
Why mount /static/grex/ writable inside a --read-only container?
Keeping the container root filesystem read-only prevents runtime tampering with application code (src/app.grab and starter templates). Mounting storage/, uploads/, and public/grex/ (/static/grex/) as explicit writable volumes lets database state, media uploads, and visual builder design tokens update safely without rebuilding containers.
